# Feature Specification: fileId 直链图片访问（新架构）

**Feature Branch**: `001-fileid-direct-link`  
**Created**: 2026-09-01  
**Status**: Draft  
**Input**: User description: "现在功能完善，但是我遇到一个数据库损坏的问题，导致我丢失了所有链接，对应的key，我的网站图片无法访问了。我只用到了图片功能，使用的是bot，实际上，每个图片，都可以通过fileId直接访问……使用 fileId 加后缀作为url，如果没有匹配到，使用 bot 直接获取图片" / 修订: "不考虑兜底，我已经完全损失数据了，当一个新项目处理；不考虑 bot 切换"

## 背景问题

此前图片访问链接由随机生成的唯一标识（UUID）组成，链接与 Telegram 文件标识（fileId）的映射仅保存在服务端数据库中。数据库已完全损坏、数据不可恢复，所有已分发链接随之失效。

**本特性按全新项目处理**：不设计"查库命中/未命中"的分支兜底逻辑，不兼容旧 UUID 链接格式（存量已全部失效，无数据可保护）。图片访问以 fileId 直链为**唯一方式**：链接由 fileId 加后缀组成，访问链路**零数据库依赖**——服务重新部署即可用，数据库损坏与否不再影响任何链接的访问。数据库仅作为管理功能（登记、统计、禁用）的可选增强，其存亡与访问无关。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 上传返回 fileId 直链 (Priority: P1)

作为图床用户，我上传图片后获得的访问链接由文件的 fileId 加后缀（文件名/扩展名）组成。链接自身携带取回文件所需的全部信息，是唯一被支持的链接格式。

**Why this priority**: 这是新架构的基础——链接包含 fileId，访问才可能脱离数据库。

**Independent Test**: 上传一张图片，检查返回链接由 fileId 与后缀组成；立即访问该链接能正常显示。仅本故事即可交付"链接自描述"价值。

**Acceptance Scenarios**:

1. **Given** 用户上传一张 PNG 图片， **When** 上传完成， **Then** 返回的链接由 fileId 与带扩展名的后缀组成，访问该链接返回原始图片
2. **Given** 用户上传一张 GIF 动图， **When** 访问返回的链接， **Then** 动图正常播放（含被 Telegram 转码为 MP4 的情况）
3. **Given** 用户分别通过网页与 API 上传， **When** 上传成功， **Then** 两种方式返回的链接均为 fileId 直链格式

---

### User Story 2 - 零数据库依赖的图片访问 (Priority: P1)

作为站长/网站访问者，访问 fileId 直链时，系统直接从链接提取 fileId，通过 bot 获取文件内容并返回。无论数据库完好、损坏还是根本不存在，访问行为完全一致。服务器损坏后只需重新部署，所有已分发的链接即刻恢复可用——无需恢复任何数据。

**Why this priority**: 这是本特性的核心价值——访问与数据库彻底解耦，直接消除"数据库损坏导致图片不可访问"这一故障模式。

**Independent Test**: 删除数据库文件（或全新部署时不创建数据库）后重启服务，此前保存的 fileId 直链全部正常访问。仅本故事（配合故事1）即交付完整核心价值。

**Acceptance Scenarios**:

1. **Given** 数据库完好， **When** 访问者请求某 fileId 直链， **Then** 图片正常返回，且访问计数正常登记
2. **Given** 数据库文件不存在或已损坏， **When** 访问者请求同一链接， **Then** 图片正常返回，访问体验与数据库完好时无差异
3. **Given** 服务在无数据库状态下全新部署， **When** 使用此前分发的 fileId 直链访问， **Then** 全部链接正常返回图片
4. **Given** 某链接中的 fileId 已失效， **When** 访问该链接， **Then** 返回明确的"文件不存在"错误（404），而非服务器内部错误
5. **Given** 访问者使用 GET / HEAD / 跨域预检 / 断点续传等既有方式， **When** 通过直链访问， **Then** 响应行为与既有访问方式一致（含缓存头与流式传输）

---

### User Story 3 - 管理功能作为可选增强 (Priority: P2)

作为管理员，上传时系统仍将图片登记到数据库，管理页面可查看记录、累加访问统计、执行禁用操作。管理功能依赖数据库，其故障只影响管理本身，绝不影响图片访问。

**Why this priority**: 保留既有管理能力但不让它反向拖累访问——管理是增强，不是访问的前提。

**Independent Test**: 数据库完好时登录管理页面，可见上传记录并可禁用；禁用后访问返回占位图。删除数据库后访问不受任何影响。

**Acceptance Scenarios**:

1. **Given** 数据库可用， **When** 上传成功， **Then** 图片被登记（含 fileId、链接、文件名、内容类型），管理页面可见
2. **Given** 数据库写入失败（如磁盘故障）， **When** 上传图片， **Then** 上传仍然成功并返回可用的 fileId 直链（登记失败不阻断上传）
3. **Given** 某图片已被管理员禁用且数据库可用， **When** 访问该图片直链， **Then** 返回已删除占位图
4. **Given** 数据库不可用， **When** 访问任何直链（含此前禁用过的）， **Then** 图片正常返回（禁用状态随数据库一同失效，为接受的取舍）

---

### User Story 4 - 从频道历史重建管理数据 (Priority: P3)

作为管理员，数据库丢失后（如本次事故），我可以触发一次"重建"操作：系统遍历存储频道的历史消息，将全部图片重新登记到新数据库，恢复管理页面的记录与检索能力。链接访问不依赖此过程，重建前后访问行为不变。

**Why this priority**: 恢复的是管理数据而非访问能力——访问已由直链保障，重建只让管理功能失而复得，可独立延后交付。

**Independent Test**: 清空数据库后触发重建，完成后管理页面展示频道内全部图片记录；重建期间与重建后，直链访问始终正常。

**Acceptance Scenarios**:

1. **Given** 数据库为空且存储频道内有历史图片， **When** 管理员触发重建， **Then** 频道内全部图片被重新登记，管理页面可见
2. **Given** 重建正在进行， **When** 访问者请求直链， **Then** 访问不受影响
3. **Given** 重建产生的记录， **When** 管理员对其执行禁用/统计， **Then** 行为与正常登记的记录一致

---

### Edge Cases

- **fileId 与后缀的切分**：fileId 由 Telegram 生成、字符集与长度不受本系统控制，链接设计必须保证 fileId 与后缀能被准确切分，不因特殊字符产生歧义
- **后缀缺失或无法识别**：内容类型需依据后缀推断，后缀不可用时需依据文件内容检测，保证浏览器正确渲染
- **禁用语义随数据库失效**：数据库故障期间，此前禁用的图片恢复可见。文件本体仍在 Telegram 频道，此为换取访问解耦的接受取舍，需向用户说明
- **无数据库的部署与启动**：服务在数据库文件缺失时应能正常启动并服务上传与访问，管理功能降级而非报错退出
- **获取频率限制**：bot 获取文件存在平台侧频率限制，需沿用既有的直链缓存策略，避免逐请求获取
- **GIF 转码**：Telegram 会将部分 GIF 转码为 MP4，需与既有逻辑一致地动态修正内容类型
- **同一图片多尺寸**：同一图片的不同尺寸对应不同 fileId，链接指向上传时登记的那一个
- **上传后立即访问**：上传返回的链接必须立即可访问，不存在登记延迟导致的空窗

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 新上传图片的访问链接 MUST 由 fileId 加后缀（文件名/扩展名）组成，且为系统唯一支持的图片链接格式
- **FR-002**: 访问 fileId 直链时，系统 MUST 直接从链接提取 fileId 并通过 bot 获取文件内容返回；访问链路 MUST NOT 以数据库查询为先决条件
- **FR-003**: 数据库不存在、损坏或无记录时，直链访问行为 MUST 与数据库完好时完全一致（唯一差异允许为统计登记不可用）
- **FR-004**: 返回内容类型 MUST 依据链接后缀推断；后缀缺失或无法识别时 MUST 依据文件内容检测
- **FR-005**: fileId 失效或通过 bot 获取失败时，系统 MUST 返回明确的文件未找到错误（404），而非服务器内部错误
- **FR-006**: 上传成功后系统 SHOULD 将图片登记到数据库（fileId、链接、文件名、内容类型）供管理使用；登记失败 MUST NOT 导致上传失败，链接仍须正常返回且可用
- **FR-007**: 既有管理功能（记录查看、访问统计、禁用）MUST 保留；禁用检查仅在数据库可用且记录存在时生效
- **FR-008**: 直链访问 MUST 支持既有的访问方式与响应行为（GET / HEAD / OPTIONS 预检、跨域头、缓存头、断点续传、流式传输）
- **FR-009**: 范围限定——仅图片（bot 上传）采用 fileId 直链新架构；文档（用户账号上传）功能维持现状；旧 UUID 链接格式废弃，不再支持；bot 切换场景不在本特性范围内（频道文件仍在，链接地址不变，但可用性恢复需另行处理）
- **FR-010**: 系统 SHOULD 提供由管理员触发的频道历史重建能力，将频道内全部图片重新登记到数据库；重建过程 MUST NOT 影响直链访问

### Key Entities *(include if feature involves data)*

- **fileId 直链**：由文件标识（fileId）+ 后缀组成的自描述访问链接，是图片访问的唯一凭据——仅凭链接与 bot 凭据即可取回文件，与数据库是否存在无关
- **图片记录**：图片在服务端的管理登记——fileId、链接、文件名、内容类型、是否禁用、访问统计、上传时间。仅服务于管理功能，可丢失、可重建，不影响访问

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 删除数据库文件（或全新部署不含数据库）后，所有已分发的 fileId 直链 100% 正常访问，且新上传—访问链路 100% 可用
- **SC-002**: 数据库完好场景下的访问体验无可感知退化——首字节时间与既有架构持平，并发访问能力不受影响
- **SC-003**: 上传完成后立即访问返回的链接，成功率 100%（含数据库写入失败时的上传）
- **SC-004**: 数据库可用时，管理页面功能（查看、统计、禁用）与既有行为一致

## Assumptions

- bot 凭据（token）与存储频道不变更：Telegram 的 fileId 与 bot 绑定；bot 切换场景按用户指示明确排除在范围外
- 文件本体持续保留在 Telegram 频道中，不在 Telegram 侧删除消息
- 图片大小在 bot 可直接获取的范围内；既有上传限制（图片约 10MB）本就满足该前提
- 数据库丢失时，禁用状态与历史访问统计随之丢失，重建前禁用语义失效——为换取访问解耦的接受取舍
- 无存量数据需要兼容：旧 UUID 链接已全部失效，本特性不做迁移、不做兼容
- fileId 直链为新项目唯一链接格式，不提供格式开关（如后续需要可经配置扩展）
- 仅图片功能采用新架构；文档功能维持现状
